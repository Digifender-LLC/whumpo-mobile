# Android Work queries

The existing Core Work surfaces use one shared query screen and controller. The local Core account surface retains its task creation, offline capture, notifications, files, calendar and recovery entry points. The native launcher keeps its existing synthetic-origin/debug gating; this change does not enable a release endpoint.

The screen reads the canonical `/v1/work/tasks` API in pages of 50, groups loaded rows by status, and shows server counts and `asOf`. Workspace, project, due date, status, customer and assignee filters use named choices. Owner-only assignee directory reads and completion controls are absent for other roles. Customer contact details are validated but not retained as display state.

A retained list owns its original release cursor, including after its final page. Filter/restart changes await DELETE acknowledgement before another initial query; a session-owned coordinator also releases an abandoned view's snapshot before a replacement view creates one. Pagination preserves counts and `asOf` and rejects duplicate rows or inconsistent continuations. Scope loss clears visible state immediately. A late cursor is released with its initiating bearer solely for cleanup; an old cleanup failure cannot sign out a replacement session. The server's two-snapshot cap and cursor-expiry behavior remain authoritative.

Task history reads canonical revisions and checks the current task's scope. Original-request navigation retains only the exact recorded user message, not unrelated conversation bodies or generated summaries. Blocked tasks link to their recorded history without inventing an unrecorded blocker reason.

Completion is an owner assertion on an in-progress task, with the displayed version sent as `If-Match` and one frozen idempotency key for retries. It reuses the existing proposal review/decision components. Pending approval or a queued effect never marks the task complete. The verified state requires matching effect, run, receipt, task version, owner assertion and a canonical task read. A later task version is shown as current state separately from the historical verified version. A fresh-owner 403 is an affordance error, not logout or a grant.

## Local evidence and remaining qualification

The first wired checkpoint compiled the shared JVM/Android code, local-debug app and AndroidTest sources and passed eight query cases. Subsequent targeted verification passed 30 existing/new Work JVM cases and one Compose host case, plus the updated launcher test-source compile. A final completion-only checkpoint passed three cases, including owner denial without logout, frozen retry/conflict, matching receipt, and pending/changed approval review. All runs used an isolated Gradle home, pinned JDK, one worker and bounded owned-process supervision. These are local compile/test results, not a physical-device or real-Worker UI proof.

The first coherent candidate passed the full local gate: 605 JVM cases, 747 host cases and two Wear cases, both debug app/test assemblies and local/deployed/Wear lint; app unit tasks reported NO-SOURCE. Review then identified a definite-conflict retry issue. Its successor allows a new assertion only on a refreshed version after a definite rejection, while preserving ambiguous/pending assertions. Three actual Surface instrumentation cases cover this selection and a non-owner with a visible in-progress task; both flavor test sources compile, but those new device tests have not yet run. The successor full local gate, final source peer, hosted API28/API36 checks and actual native Work acceptance remain pending at this checkpoint. No private backend fixture, credential, local Worker database or private evidence is included in this public repository. No delete/archive policy, backend schema, billing or provider behavior changes are made.
