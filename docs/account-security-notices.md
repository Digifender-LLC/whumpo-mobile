# Account security notices

The account-security screen reads metadata from the closed `GET /v1/account-security/notices` contract using an `AccountGrant`. A signed-in account can read notices without any current organization membership. This does not establish workspace authority: organization listing and explicit workspace entry retain their existing access checks.

The response contains only `items` and nullable `nextCursor`. Each of at most 20 items contains `id`, `kind`, `createdAt` and `delivery` (`sent`, `unknown`, or `not_configured`). IDs and cursors use the bounded account-security opaque identifier format. Unknown fields, malformed timestamps, duplicate page IDs, changed repeated rows, cursor loops and nonprogressing continuations are rejected. A read is limited to twenty continuations and 420 unique records.

The screen offers Show, Refresh, More and Hide controls, including for accounts with no workspace access. It displays generic security-event dates and human delivery statuses. It does not expose credential material or start workspace sessions. Hide, screen disposal, grant replacement, account clearing and expiry discard notice state. Replies are fenced by the current account epoch, grant object, notice revision and expiry; a matching HTTP 401 clears current authority, while obsolete replies cannot alter a later account.

Verification plan: synthetic Ktor MockEngine controller tests cover account-grant transport, zero-organization reads, closed decoding, pagination/dedupe limits, held responses after Hide and expiry, cancellation and current 401. Plain Compose host tests cover visible controls, callbacks, busy state and private-row removal. Existing account enrollment and explicit organization-entry tests remain required. Normal credential-free local and hosted Android gates are required before integration. This document records implementation intent; it does not claim completed verification, real-service, device, or accessibility acceptance.
